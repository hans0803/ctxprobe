# RTX 5090 32GB — DeepSeek-V4-Flash-0731（UD-IQ4_XS）

[English](rtx5090-32gb-deepseek-v4-flash.md) · **繁體中文**

實測於 2026-08-11。一個 136.66 GB 的模型，跑在單張 32 GB 顯卡上，
expert 放在系統記憶體裡。這是 [Gemma4-26B-A4B](rtx5060ti-16gb-gemma4-26b-a4b.zh-TW.md)
帶出的 MoE offload 案例的極端版本：在那裡，把 expert 移出去讓權重從
14.44 GB 掉到 2.4 GB；在這裡，它讓一個 137 GB 的模型**根本裝得進**消費級顯卡。

## 硬體與模型

| | |
|---|---|
| **GPU** | **NVIDIA GeForce RTX 5090 — 回報 32607 MiB，可配置 32109 MiB** |
| 驅動保留區 | **498 MiB**（16 GB 卡是 462 —— 卡越大保留越多） |
| CPU | AMD Ryzen 9 9950X，16 核 / 32 執行緒 |
| 記憶體 | **192 GB DDR5-5600**，雙通道 |
| llama.cpp | `4801e3c`（2026-08-10）—— `LLM_ARCH_DEEPSEEK4` 在 6/26 之後才進來 |
| 模型 | [unsloth/DeepSeek-V4-Flash-0731-GGUF](https://huggingface.co/unsloth/DeepSeek-V4-Flash-0731-GGUF) `UD-IQ4_XS`，**136.66 GB**，4 個分片 |

這台的第二張 5090 正在服務其他東西；以下全部只用單卡
（透過 `CUDA_VISIBLE_DEVICES=1`）。

架構，取自 GGUF metadata：

```
deepseek4.block_count       = 43
deepseek4.expert_count      = 256
deepseek4.expert_used_count = 6      <- 256 選 6
deepseek4.attention.key_length = 512  (MLA)
deepseek4.context_length    = 1048576
```

**約 280B 參數中有 277B 是 expert。** 這正是它能成立的原因：
`--cpu-moe` 幾乎把整個模型都搬走了，留在 GPU 上的只有
attention、embedding 和 shared expert。

## 它跑得起來，而且 context 不是限制

| Context | 結果 | 峰值顯存 | Prefill | 生成 |
|---|---|---|---|---|
| 8,192 | PASS | 8927 MiB | 153.86 tok/s | 13.28 tok/s |
| **131,072** | **PASS** | 10441 MiB | 153.83 tok/s | 13.32 tok/s |

131,072 是 **當時 ctxprobe 的搜尋上限，不是模型的極限** ——
二分搜尋只跑兩次就結束，因為上界本身就通過了。模型宣告的是 1,048,576。
上限後來已提高到 262,144；在重新量測之前，這一列是下界。

這兩列都通過了 prompt 階梯（64/512/4096），但當時沒有通過 95% 填充驗證：
在 153 tok/s 之下，131,072 的驗證 prompt 需要 124K token 的 prefill ——
13 分鐘 —— 所以被中止了，131,072 當時只能算*階梯已驗證、完整驗證未完成*。

**2026-08-31 補驗通過**，靠的是底下那個 ubatch 發現讓它變得可行
（775 tok/s 而不是 153），以及一個會在滿視窗失敗時往下二分的 ctxprobe：

```
Validating 131072 at 95% fill...
  confirmed: 131072 (124075 tokens filled)
  peak VRAM 15469 MiB | prefill 653.41 tok/s | generate 11.92 tok/s
```

`-ub 8192` 之下兩分半跑完。階梯在這裡是對的。
值得說明為什麼，因為在 [Qwen3.8-Flash-Next](rtx5090-32gb-qwen3.8-flash-next.zh-TW.md)
上 —— 同樣是稀疏注意力、同樣有一個暫存區隨 `n_kv` 長大的 indexer ——
階梯把天花板高估了 41%。差別不在機制，在餘裕：
這個配置的峰值是 15,469 / 32,109，所以不管 indexer 的工作集在 124K 視窗下變多大，
它有 16 GB 可以長。Qwen3.8-Flash-Next 當時只剩 10 MiB。
**會長大的 buffer 只有在卡滿的時候才會變成天花板。**

驗證出來的速度比表裡低，本來就該如此：對著 124K token 的視窗是 653 tok/s prefill、
11.92 tok/s 生成，而表裡的 154 和 13.32 是 `-ub 512` 對著短 prompt 量的。
峰值顯存是 15,469 而不是 10,441，原因跟 ubatch 那張表顯示的一樣 ——
compute buffer 是按 `-ub` 配置的，而這次跑的是 8192。

KV 成本換算約為**每 token 12.3 KB**（由兩列之間 1,514 MiB 的差反推）。
MLA 在這裡便宜得驚人：Qwen3.6-27B 是每 1K token 34 MiB，這裡是 12.3 KB ——
差了 2,800 倍。

扣掉 KV 的基礎顯存約 **8.8 GB**。這遠高於單看參數量的推算（約 2.3 GB）；
這版 llama.cpp 不印 buffer 分配，所以組成尚未拆解。
這裡按實測值呈現，而不是硬套解釋。

## 系統記憶體要多少

顯卡是這套部署裡便宜的那一半。expert 總得住在某個地方，而那個地方是 RAM。

同一組設定（`--cpu-moe -ub 8192 -c 24576 --threads 28`），
唯一的差別是 llama.cpp 怎麼把檔案讀進記憶體：

| | mmap（預設） | `--no-mmap` |
|---|---|---|
| 載入時間 | **4 秒** | **75 秒** |
| 行程 RSS | 131,061 MiB | 124,730 MiB |
| 系統 `used` 增長 | **+1.8 GB** | **+126 GB** |
| 載入後 `available` | 177 GB | 53 GB |
| 生成，3 × 256 token | 12.03 / 12.08 / 12.07 | 12.07 / 12.08 / 12.12 |

**在 mmap 之下，RSS 會騙人。** 行程回報 131 GB 常駐，
系統的 `used` 卻只增加 1.8 GB，因為那些頁面是支撐檔案映射的 page cache ——
共用、乾淨、可回收。把 RSS 讀成「這個行程需要 131 GB 記憶體」是往一個方向錯，
把那 1.8 GB 當成需求則是往另一個方向錯。

**`--no-mmap` 在這裡什麼都換不到。** 只要 CPU 張量覆寫和 mmap 同時出現，
llama.cpp 就會印 `consider using --no-mmap for better performance`，
看起來像是白撿的。實測下來，生成速度差距在 0.4% 以內 ——
同一個數字重複三次 —— 代價卻是 126 GB 核心無法回收的**匿名**記憶體，
以及 19 倍的載入時間。映射一旦完全常駐，`--no-mmap` 就沒有東西可以修了。

`--no-mmap` 的 RSS 比 130,332 MiB 的檔案還**少** 5.6 GB，
這是一個有用的對帳：那就是非 expert 的張量，
它們去了 GPU，從來沒有在 RAM 裡被配置過。

### 實際上需要多少

路由讓這件事很單純。每個 token 在每一層從 256 個 expert 裡挑 6 個，
所以相鄰的 token 碰到的 expert 不同，累積幾十個 token 之後，
你基本上已經全部碰過一輪。**不存在比模型本身更小的工作集。**

> **系統記憶體 ≥ 模型檔案大小 + 約 10 GB。**

這個模型的權重是 130,332 MiB，所以：

| 記憶體 | 結論 |
|---|---|
| 96 GB | 不行。每個 token 都要從磁碟 fault，速度會掉到「每個 token 幾*秒*」 |
| 128 GB | 勉強 —— 光檔案就 127.3 GiB，作業系統沒有空間了 |
| **192 GB** | **充裕。** 即使在 `--no-mmap` 的最壞情況下，這裡仍剩 53 GB |

記憶體不夠時的失敗形態**不是報錯**。它會載入、會回答，然後慢到無法使用，
因為 page cache 是在跟儲存裝置來回抖動，而不是在讀 DDR5 ——
形狀跟記憶體層級再下一層的溢出問題一模一樣。

盯著 `buff/cache` 看：這台機器在模型熱的時候它停在約 160 GB，
而那個數字**就是**模型常駐在記憶體裡這件事本身。

## 速度受頻寬限制，而且算式對得上

137 GB 的 expert 放在 DDR5 卻還有約 13.3 tok/s，
乍看令人意外，把路由算進去就合理了：

```
每個 expert   3 × 4096 × 2048 = 25.17M 參數
每個 token    43 層 × (6 routed + 1 shared) = 301 個 expert
              301 × 25.17M × 約 0.49 bytes ≈ 每 token 3.7 GB

13.3 tok/s × 3.7 GB = 49 GB/s
```

這台主機實測：copy 37.0 GB/s、單執行緒讀 35.4 GB/s。
多執行緒之下的 49 GB/s，與一條被打滿的雙通道 DDR5-5600 是一致的。
**它就是頻寬受限，正如一個 4B active 的模型跑在 DDR5 上該有的樣子。**

這個 49 GB/s 略為低估，因為它是除以整個 token 的時間。
下面[那條縮放定律](#這條縮放定律)把 16.0 ms 的固定成本分離出來 ——
那一段不是記憶體流量 —— 剩下 3.7 GB 除以 66.8 ms，
expert 讀取本身其實是 **55 GB/s**。

## ubatch 這個發現

Prefill 一開始只有 153 tok/s —— 比一張弱得多的卡上的 Gemma4 慢 23 倍。
原因是 prefill 會讓稀疏性失效：在一個 512 token 的 ubatch 裡，
每個 token 各選 256 個中的 6 個，所以整批加起來幾乎會碰到全部。
**每個 ubatch 實際上都要把某一層的 expert 集合整個讀一遍**，
而這個成本是攤提在「這一批裡有多少 token」上面的。

掃描 `-ub`（`-b` 同步跟上），20,480 token 的 prompt，`-c 24576`：

| ubatch | 峰值顯存 | Prefill | 相對 512 | 生成 |
|---|---|---|---|---|
| 512（預設） | 9057 MiB | 151.51 | — | 12.38 |
| 1,024 | 9291 MiB | 259.66 | 1.7× | 12.32 |
| 2,048 | 9767 MiB | 426.83 | 2.8× | 12.26 |
| 4,096 | 10649 MiB | 649.81 | 4.3× | 12.12 |
| **8,192** | **12509 MiB** | **775.35** | **5.1×** | 12.07 |
| 16,384 | 17503 MiB | 782.03 | 5.2× | 11.75 |
| 24,576 | 23003 MiB | 767.27 | 5.1× | 11.67 |

**8,192 就是轉折點。** 再往上 prefill 在雜訊範圍內持平，
顯存卻從 12.5 GB 一路爬到 23 GB —— compute buffer 是按 ubatch 配置的，
不管 prompt 有沒有填滿它。
生成速度全程幾乎不動（12.38 → 11.67），
這正是讓 prefill 結果無可爭議的對照組：batch 為 1 的解碼不在乎 ubatch。

轉折點不是一個常數。8,192 把這個 20K 的 prompt 切成 3 批，
到那時 expert 的讀取已經攤提得差不多了。
實用值大致會跟著「大到能把你的 prompt 切成 2~3 批」走。

### 收益從哪裡開始

同一個模型，`-ub 512` 對比 `-ub 8192`，量的是實際的首 token 牆鐘時間：

| Prompt | `-ub 512` | `-ub 8192` | 加速 |
|---|---|---|---|
| 140 | 2,974 ms | 2,998 ms | 1.00× |
| 249 | 3,370 ms | 3,400 ms | 0.99× |
| 511 | 3,894 ms | 3,929 ms | 0.99× |
| 998 | 6,857 ms | 4,312 ms | **1.59×** |
| 2,020 | 13,390 ms | 5,133 ms | **2.61×** |

**512 以下毫無差別，超過就全部有差。** 斷點精確落在 `n_ubatch` 上，
這是機制自己顯現出來，而不是被論證出來的。

從 `-ub 512` 那一欄還掉出兩件事：

- 每多一個 ubatch 就多約 **3 秒**，跟這一批裡有幾個 token 無關。
  那就是透過 DDR5 把某一層的 expert 掃一遍的代價。
- 即使是 140 token 的 prompt 也要等約 3 秒。
  **在這種部署形態下，TTFT 有一個約 3 秒的地板** —— 第一次 expert 掃描躲不掉。

所以 `-ub 8192` 的代價是 3.5 GB 顯存，
對短對話回合一文不值，對「有系統提示加一些歷史」的 prompt 值 1.6~2.6 倍，
對文件則是 5 倍。在一張還有約 20 GB 空著的 32 GB 卡上，沒有理由不開。

## 把一部分 expert 留在 GPU 上

`--cpu-moe` 會把所有 expert 都趕走。`--n-cpu-moe N` 則是把前 N 層的 expert
留在系統記憶體，所以 N 越小、留在卡上的越多。單卡、`-ub 8192`、`-c 24576`：

| `--n-cpu-moe` | GPU 上層數 | 峰值顯存 | Prefill | 生成，3 × 256 token |
|---|---|---|---|---|
| 43（= `--cpu-moe`） | 0 | 12,243 MiB | 621.11 | 12.09 / 12.04 / 12.07 |
| 41 | 2 | 17,939 MiB | — | 12.53 / 12.57 / 12.57 |
| 40 | 3 | 20,787 MiB | 643.99 | 12.73 / 12.85 / 12.86 |
| 39 | 4 | 23,635 MiB | — | 12.92 / 13.07 / 13.08 |
| **38** | **5** | **26,481 MiB** | 669.30 | **13.33 / 13.35 / 13.35** |
| 36 | 7 | ✗ OOM | — | — |

顯存的級距完全線性 —— **每多一層 2,848 MiB**。
這個數字準確預測了下面每一項容量結果，
所以任何你打算手動放置的模型，都值得先推出這個係數。

32 GB 的上限是 5 層，代價是 **14 GB 換 +11% 生成速度**。

### 這條縮放定律

這五個點落在同一條線上。把每 token 的時間對「還留在 RAM 裡的 expert 層比例」作圖：

```
t_token  =  16.0 ms  +  66.8 ms × (43 − K) / 43        K = 放在 GPU 上的層數
```

每個實測點都落在這條線的 0.2 ms 之內：

| K | 實測 | 預測 |
|---|---|---|
| 0 | 82.85 ms | 82.8 |
| 2 | 79.62 ms | 79.7 |
| 3 | 78.06 ms | 78.1 |
| 4 | 76.80 ms | 76.6 |
| 5 | 74.96 ms | 75.0 |

這兩項就是這種部署形態的全部故事：

- **16.0 ms 是固定成本。** attention、shared expert、router、
  kernel 啟動與同步。再多顯存都拿不掉它，而它定義了天花板：
  就算每一個 expert 都在卡上，這個模型也只能到大約 **62 tok/s**。
- **66.8 ms 是 DDR5 的 expert 讀取**，而這是顯存唯一買得回來的部分 ——
  而且嚴格按照「搬走了多少*比例*的層」等比縮小。

正是這個等比關係讓顯存在這裡成為一筆很差的採購。
每一層固定要 2,848 MiB、固定省下 1.55 ms，
所以每 GB 的回報大致是常數，而被改善的那個東西本來就已經很小了：

| 目標 | 需要層數 | expert 顯存 | 總顯存 | 硬體 |
|---|---|---|---|---|
| 12 tok/s（基準） | 0 | 0 | **12.3 GB** | 一張 16 GB 卡 |
| 13.3 tok/s（+11%） | 5 | 13.9 GB | 26.5 GB | 一張 32 GB 卡 |
| 18 tok/s（+50%） | 約 18 | 50 GB | 約 60 GB | 兩張 32 GB 卡 |
| 24 tok/s（+100%） | 約 27 | 76 GB | **約 85 GB** | 三張 32 GB 卡 |
| 62 tok/s（天花板） | 43 | 120 GB | 約 128 GB | 四張 32 GB 卡 |

5 層以上的列是從擬合外推的，不是實測；
下面的雙卡那一節是唯一測過的一個外推點 —— 而它沒有成立。

### 兩張卡

兩張 5090，把 expert 明確分配到兩張卡上。層範圍平均切開，每個 `-ot` 一組 regex：

| GPU 上層數 | GPU0 + GPU1 | 總計 | Prefill | 生成 |
|---|---|---|---|---|
| 7 | 19,775 + 16,873 | 36.6 GB | 718.85 | 13.84 |
| 13 | 25,471 + 28,263 | 53.7 GB | 821.51 | 15.86 |
| 14 | 28,319 + 28,263 | 56.6 GB | 841.92 | 13.70 |
| 15 | 31,167 + 28,263 | 59.4 GB | 860.60 | 14.34 |
| 16 | 31,167 + 31,111 | **62.3 GB** | **884.79** | 13.38 |
| 17 | ✗ OOM | 預估 65.1 GB | — | — |

容量表現跟每層 2,848 MiB 的推算完全一致：
16 層是 62.3 GB，對比可配置的 64.2 GB，剛好過；17 層就不行。

考慮到 `-ot` 失敗時有多安靜，光看顯存就能驗證放置是否生效，值得做一次。
每一列都吻合「兩個基準值（8,381 與 8,329 MiB）之上每層 2,848 MiB」，
誤差在 3 MiB 以內：

| 要求 | GPU0 | 推算 | GPU1 | 推算 |
|---|---|---|---|---|
| 4 + 3 層 | 19,775 | 8,381 + 4×2,848 = 19,773 | 16,873 | 8,329 + 3×2,848 = 16,873 |
| 6 + 7 層 | 25,471 | 25,469 | 28,263 | 28,265 |
| 8 + 8 層 | 31,167 | 31,165 | 31,111 | 31,113 |

2,848 MiB 就是**某一層全部 256 個 expert** —— 43 × 2.98 GB 剛好對得上 128 GB 的檔案。
所以每一層要嘛整層在卡上、要嘛整層在 RAM 裡，
**路由不可能把某個 expert 拉到卡外**。這排除了生成那一欄最直覺的解讀。

**Prefill 是單調的**（719 → 885，整段 +23%），
因為 ubatch 解決頻寬問題之後它就變成計算受限，而多一張卡就是多一份算力。

**生成那一欄不可信。** 這些列只取樣 32 個生成 token，那不足以計時 ——
單卡梯度用 256 token 重跑之後，散布收斂到 ±0.2%。
請把雙卡的生成數字讀成「13～16，順序無法分辨」，
並注意縮放定律預測 **16 層應該有 17.3 tok/s**，比這裡量到的任何一個都高約 25%。
究竟是第二張卡真的兌現不了這條定律，還是取樣本身太短，**目前無解**；
這需要用 256 token 重測一次。

這份紀錄先前把這個散布解釋成「逐 token 的路由讓 expert 進出顯卡」。
上面的放置算式排除了這個可能。
它被記在 [gotchas 第 10 條](../docs/gotchas.zh-TW.md)，當作一個錯誤保留下來。

### 第二張卡值得嗎

| 配置 | 生成 | Prefill | 顯存 |
|---|---|---|---|
| 單卡，`--cpu-moe` | **12.07** ± 0.2% | 621 | **12.3 GB** |
| 單卡，`--n-cpu-moe 38` | **13.34** ± 0.1% | 669 | 26.5 GB |
| 雙卡，13～16 層 | 13～16，無解 | 821 – 885 | 53.7 – 62.3 GB |

Prefill 才是第二張卡誠實的理由：**+23%，而且是在幾千個 token 上計時出來的**，
這個數字站得住。但對照 `-ub 8192` 用 3.5 GB 換到 5.1 倍 prefill，匯率仍然很差。

至於生成，第二張卡**無法被證明**買到了任何超過單卡 13.34 的東西 ——
而依照定律，它最多也只能買到 +30%。

## 沒有用的東西

**`--tensor-split` 在這裡毫無作用。** `1,1` 和 `3,1` 在 13 層時都載入失敗，
而第一次沒有用 `-ot` 的雙卡嘗試，GPU0 停在 8.4 GB、GPU1 卻衝到 31.1 GB。

原因是兩個機制疊在一起的結果很糟。Layer split 是**連續的**：
GPU0 拿前段的一批層，GPU1 拿其餘。而 `--n-cpu-moe N` 留在 GPU 側的 expert
位於**最後** N 層 —— 那是一整段連續的層，會完全落在同一張卡上。
移動切點沒辦法把它們拆開，只有明確指名張量才行。

有兩種會讓 `-ot` 靜默失效的寫法，兩種我都踩過，
而且都先產出了一整張看起來合理的數字才被抓到：

```bash
# 錯 —— CPU pattern 寫在前面，把全部都吃掉了
-ot "blk\.(3[0-9])\.ffn_.*_exps\.weight=CPU" -ot "blk\.30\..*=CUDA0"

# 錯 —— 貪婪的 .* 把逗號分隔符也吞了，結果什麼都沒匹配到
-ot "blk\.36\.ffn_.*_exps\.weight=CUDA0,blk\.37\.ffn_.*_exps\.weight=CUDA0"

# 對 —— 每個旗標一組 regex 範圍，而且 -ot 放在 --cpu-moe 之前
-ot "blk\.(3[0-5])\.ffn_.*_exps\.weight=CUDA0" \
-ot "blk\.(3[6-9]|4[0-2])\.ffn_.*_exps\.weight=CUDA1" \
--cpu-moe
```

兩種錯誤都不會報錯。辨識的方法是看顯存有沒有停在
「零 expert 在 GPU」的基準值 —— 這裡是 8,381 + 8,329 MiB ——
同時生成速度維持在全 CPU 的數字。

## 這件事對買硬體的意義

一旦模型裝不進顯存，**顯存就不再是值得買的那個東西**。

| 顯存 | 配置 | 生成 | 需要的卡 |
|---|---|---|---|
| **9.1 GB** | `--cpu-moe`、`-ub 512` | 12.4 | 12 GB |
| **12.3 GB** | `--cpu-moe`、`-ub 8192` | 12.07 | **16 GB** |
| 26.5 GB | `--n-cpu-moe 38` | 13.34 | 32 GB |
| 62.3 GB | 雙卡 16 層 | 13～16 | 兩張 32 GB |

**一個 137 GB 的模型，在一張 16 GB 卡上跑 12 tok/s。**
五倍的顯存，換到的是確認過的 +11%。
原因就在縮放定律裡：你以每層 2,848 MiB 的線性代價買 expert 層，
而每一層固定回報 1.55 ms，對照的是一個 74～83 ms 的 token。
在模型大部分都常駐之前不會發生任何有趣的事，
而「一個 137 GB 模型的大部分」不是消費級的採購。

16 GB 而不是 12 GB，是額外顯存唯一明確划算的地方，
而且那不是為了權重：它買的是 `-ub 8192`，
值 **3.5 GB 換 4.1 倍 prefill**。再往上就是在買一條雙曲線平坦的那一段。

所以建議的形狀是反過來的：

> 買**剛好裝得下 attention、KV 和一個 8192 compute buffer** 的最小張卡。
> 其餘的錢放到記憶體 —— 先買容量，讓模型真的能常駐；
> 再買頻寬，因為那才是真正決定速度的東西。

頻寬是還沒測過的那根槓桿，而定律說它是大的那一根。
66.8 ms 的 expert 讀取，是每 token 3.7 GB 走在一條已經打滿的雙通道匯流排上。
換到約 200 GB/s 的 8 通道平台，這一項會掉到約 17 ms，
整個 token 變成約 33 ms —— **約 30 tok/s，靠的是記憶體控制器而不是顯存**。
這是從擬合外推的，不是實測，而且 16.0 ms 那個固定項未必撐得過平台更換；
但它是 2.5 倍，對照的是 2 倍所需要的約 85 GB 顯存。

### 這套結論不能推廣到 MoE 之外

整個論證建立在「每個 token 只讀 256 個 expert 中的 6 個」之上。
dense 模型每個 token 讀**全部**，所以同樣的「讓系統記憶體接住溢出」這一招會崩掉。
在同一個模擬 8 GB 預算下實測，見
[spill-cost.zh-TW.md](../docs/spill-cost.zh-TW.md)：

| | 放在系統記憶體的部分 | 用掉的顯存 | 生成 |
|---|---|---|---|
| Gemma4-26B-A4B（MoE） | expert，透過 `--cpu-moe` | 2.4 GB | **39.7 tok/s** |
| Qwen3.6-27B（dense） | 65 層中的 37 層，透過 `-ngl 28` | 約 8 GB | **5.1 tok/s** |

同一張卡、同樣裝不下，代價差了 8 倍。
對稀疏 MoE 而言，裝不下是一個可以接受的取捨，而卡應該往小的挑。
對 dense 模型而言，裝不下本身就是問題，
答案是換更小的量化或更小的模型 —— 絕不是加更多系統記憶體。

## 實用配置

```bash
llama-server -m DeepSeek-V4-Flash-0731-UD-IQ4_XS-00001-of-00004.gguf \
  -ngl 999 -c 131072 --parallel 1 --cpu-moe \
  -b 8192 -ub 8192 --threads 28
```

`--threads 28` 留 2 個實體核心給這台上的其他服務；
代價大約是 7% 的生成速度（13.3 → 12.4 tok/s），
因為 DDR5 的讀取是由 CPU 執行緒驅動的。

`--cpu-moe` 在這裡不是選配 —— 沒有它，模型根本載入不了。
