# 模型量化：你該下載哪一個？

[English](model-quant.md) · **繁體中文**

一個 GGUF 模型會有十幾個變體，名字像 `Q4_K_M`、`IQ4_XS`、`Q5_K_S`。
它們是同一個模型的不同精度版本。這份文件談的是：
當你只有一張顯卡、顯存固定時，該怎麼挑。

## 最重要的一條規則

**「能完整塞進顯存的最大量化」勝過「塞不進去的更好量化」。**

只要模型有任何一部分溢出到系統記憶體，每個 token 都得跨過 PCIe 匯流排。
那個變慢不是輕微的，而且更高精度帶來的品質提升完全補不回來。

實測：同一張卡、同一個模型、同一種量化，只有「裝得下多少」不同：

| | 生成速度 |
|---|---|
| 65 層全部在顯存 | 約 26 tok/s |
| 65 層中只有 28 層在顯存（其餘在 DDR4） | **5.11 tok/s** |

**溢出 57% 的層，速度只剩五分之一。**
「裝得下」是首要條件；品質是在「裝得下的範圍內」才去優化的東西。
細節、以及什麼時候溢出反而是對的選擇，見 [spill-cost.zh-TW.md](spill-cost.zh-TW.md)。

## 看懂那些名字

數字是最重要的：**每個權重幾個 bit**。

| 名稱 | 約略 bits | 意義 |
|---|---|---|
| `Q8_0` | 8.0 | 幾乎無損，體積是 Q4 的兩倍 |
| `Q6_K` | 6.6 | 很好，但很少有必要 |
| `Q5_K_M` | 5.7 | 裝得下的話是不錯的中間選擇 |
| `Q4_K_M` | 4.8 | 最常被推薦的預設值 |
| `Q4_K_S` | 4.5 | 稍微小一點、稍微差一點 |
| `IQ4_XS` | 4.25 | Q4 等級中最小的；製作時需要 imatrix |
| `Q3_K_M` | 3.9 | 開始出現可察覺的劣化 |
| `IQ3_XXS` | 3.1 | 只有在其他都裝不下時才用 |

那些字母：

- **`K`** —— 「K-quants」，現行的標準方案。不同的張量給不同精度，
  因為有些張量比其他的重要。
- **`S` / `M` / `L`** —— 同一家族裡的小 / 中 / 大。
- **`I`** —— 「importance matrix」量化。會先跑一次校準來決定哪些權重要保護，
  所以表現比它的 bit 數看起來更好。`IQ4_XS` 明顯打得比 4.25 bits 該有的水準高。

## 名字決定不了 bits

上面那張表刻意寫成「大約」。兩個檔案可以掛著同一個量化名字，
每權重的 bits 卻差半個 —— 因為「動態」打包（Unsloth 的 `UD-` 前綴，
以及其他家的對應做法）是逐 tensor 分配精度，而不是全檔套同一套方案。

用 ggml 各型別實際的 block 大小算出來的 bits per weight，
同一個架構的兩個版本：

| | 參數量 | tensor bytes | **bpw** |
|---|---|---|---|
| Qwen3.6-27B `IQ4_XS` | 26.90 B | 14,714 MiB | **4.5892** |
| Qwen3.8-27B `UD-IQ4_XS` | 27.32 B | 13,582 MiB | **4.1703** |
| Qwen3.8-27B `UD-Q4_K_S` | 27.32 B | 14,636 MiB | **4.4939** |

中間那一列的參數比第一列**多**，檔案卻**小**，而它的名字讓人以為兩者是同一種東西。
它是由 12 種不同的量化型別組成的（第一列只有 4 種），
其中 0.80 B 參數低於 3 bits，`token_embd` 從 `Q4_K` 掉到 `Q3_K`。

**這不是在抱怨打包方式，是在警告「比較」這件事。**
在一張 16 GB 的卡上，那 0.42 bpw 值 27,000 個 token 的 context，
所以一個「新模型 + 更省的檔案」看起來會像是很大的世代進步，而它不是。
拉到同精度來比，兩者相差不到 1.5%：

| | 天花板，q8_0 KV |
|---|---|
| Qwen3.6 `IQ4_XS`（4.5892 bpw） | 34,816 |
| Qwen3.8 `UD-IQ4_XS`（4.1703 bpw） | 61,952 |
| Qwen3.8 `UD-Q4_K_S`（4.4939 bpw） | 34,304 |

完整實測：[rtx5060ti-16gb-qwen3.8-27b.zh-TW.md](../results/rtx5060ti-16gb-qwen3.8-27b.zh-TW.md)。

要在相信一個檔案的標籤之前先驗它，做個除法就好：
**檔案 bytes × 8 ÷ 參數量**。
兩個數字 Hugging Face 的模型頁上都有，llama.cpp 載入時也會印參數量。
14,252,845,984 × 8 ÷ 27.32 B = 4.17，
這已經足以分辨一個 4.2 bpw 的檔案和一個 4.6 bpw 的檔案。
逐 tensor 的拆解需要一支 GGUF parser，但你很少需要它 ——
決定裝不裝得下的是平均值。

## 算出什麼裝得下

先粗算，然後驗證：

```
磁碟上的檔案大小  +  你要的 context 所需 KV cache  +  約 1 GB 開銷  <  可用顯存
```

這裡有兩件常被搞錯的事，兩個都會實際吃掉你的餘裕：

- **可用顯存不是 `nvidia-smi` 印出來的數字。** 一張 16 GB 的卡有約 460 MiB
  是驅動保留區，所以真正的上限大約是 15.85 GB。
- **同一張卡上的桌面環境可能佔掉 600 MiB 以上。** 見 [gotchas.zh-TW.md](gotchas.zh-TW.md)。

本專案的一個實例 —— 16 GB 卡上的 Qwen3.6-27B：

| 量化 | 大小 | 裝得下嗎 |
|---|---|---|
| `Q4_K_M` | 16.82 GB | 不行 —— 還沒算 KV cache 就已經比整張卡大 |
| `Q4_K_S` | 15.86 GB | 不行 —— 沒有空間留給 KV cache 和開銷 |
| **`IQ4_XS`** | **15.44 GB** | **可以 —— 搭配 q8_0 KV 可到 34,816 context** |
| `Q3_K_M` | 13.59 GB | 可以，而且餘裕大得多 |

一般的建議是「用 `Q4_K_M`」。在這張卡上，那個建議根本跑不起來。
`IQ4_XS` 才是裝得下的最大 Q4 等級量化，所以在這裡它才是正確答案 ——
而你只有把大小拿去對照你「實際那張卡」才會發現這件事。

## 大模型還是好量化？

在顯存預算固定的情況下，你可以選「大模型低精度」或「小模型高精度」。
通常的結論是：**大模型會贏，直到大約 4 bits 為止**，
低於大約 3 bits 之後就不成立了。

所以 27B 的 `IQ4_XS` 一般會比 14B 的 `Q8_0` 更好用 ——
但 27B 的 `IQ2` 通常就比 14B 的 `Q4_K_M` 差了。
把大約 4 bits 當成值得追求的底線，然後挑「能達到這個底線的最大模型」。

## 那 NVFP4、AWQ、GPTQ 呢？

那是另一個生態系。它們跑在 vLLM / TensorRT 而不是 llama.cpp，
而且 **vLLM 無法 offload 到 CPU** —— 模型裝不下就是啟動不了。

還有，名字會騙人。Qwen3.6-27B 的兩個 NVFP4 版本都**比** GGUF 的 Q4 **還大**，
因為「NVFP4」是混合精度：只有 MLP 張量是 4-bit，
attention 維持 FP8，其中一個版本連視覺塔都還留在 BF16。

| 版本 | 大小 |
|---|---|
| nvidia NVFP4 | 21.94 GB |
| unsloth NVFP4 | 23.44 GB |
| GGUF `IQ4_XS` | **15.44 GB** |

對單張消費級顯卡來說，GGUF 通常是唯一裝得下的選擇。

## 然後確認它真的跑得動

大小只告訴你什麼載入得了，不會告訴你什麼撐得過一個完整的 context 視窗 ——
那正是這個工具存在的理由：

```bash
ctxprobe model.gguf
```
