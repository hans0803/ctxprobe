# KV cache 量化：為什麼你多半該用 q8_0

[English](kv-cache-quant.md) · **繁體中文**

如果你只有一張消費級顯卡、又想要長 context，這是你手上槓桿最大的一個設定。
這份文件說明它做什麼、代價是什麼，用實測數字而不是經驗法則。

## KV cache 是什麼

模型讀你的 prompt 時，每個 token 在每一層 attention 都會產生兩個向量 ——
**key** 和 **value**。這些會被留著，這樣生成第 5000 個 token 時，
就不用把第 1 到 4999 個 token 從頭再讀一次。這個儲存區就是 KV cache。

重點在於：**它會隨 context 長度線性成長，而且跟模型權重一起住在顯存裡。**

```
顯存 = 模型權重（固定） + KV cache（隨 context 成長） + 其他開銷
```

權重是一次性的成本。KV cache 才是決定你拿到 8K 還是 34K context 的那一項。

## 量化它做了什麼

llama.cpp 預設用 16-bit 精度（`f16`）儲存這些向量。
加上 `--cache-type-k q8_0 --cache-type-v q8_0` 就改用 8-bit ——
聽起來像是「同樣的 token 數、記憶體減半」，但並不完全是；見[下方](#它省的是-40不是-50)。

在 RTX 5060 Ti 16GB + Qwen3.6-27B-IQ4_XS 上的實測：

| KV 型別 | 每個值幾 bit | 這張卡的最大 context |
|---|---|---|
| `f16`（預設） | 16 | 20,224 |
| **`q8_0`** | 8 | **34,816** |
| `q4_0` | 4 | 本專案尚未測試 |

兩個數字都是實測、不是估算 ——
見 [results](../results/rtx5060ti-16gb-qwen3.6-27b.zh-TW.md)。

**一個參數換到多 72% 的 context。** 模型其他部分完全不變：
一樣的權重，權重本身帶來的輸出品質也一樣。

注意它**不是**加倍，即使 cache 的體積確實減半了。
權重是 cache 碰不到的固定成本 —— 在這張卡上，15.85 GB 可用容量裡有 15.44 GB 是模型，
只剩約 400 MiB 是 cache 的預算。把每個 token 的成本減半，
延長的是那塊剩餘量，不是整個視窗。**模型塞得越緊，收益就越小** ——
在指望 q8_0 能拯救一個勉強載入的模型之前，這點值得先知道。

## 它省的是 40%，不是 50%

`q8_0` 每個值佔 1.0625 bytes，`f16` 佔 2，所以「減半」是很自然的預期。
但一張卡實際上每個 token 少付的，量出來比那個差。

峰值顯存對 context 的關係線性到可以直接從相鄰的 PASS 列讀出斜率。
以 Qwen3.8-27B 實測 —— 它有 16 層 full attention、4 個 KV head、`head_dim` 256，
也就是每 token 32,768 個 cache 數值：

| | 理論 | 實測 | 超出 |
|---|---|---|---|
| `f16` | 64.0 MiB/1K | **63.48** | 約 0 |
| `q8_0` | 34.0 MiB/1K | **38.09** | **+4.1** |

f16 的斜率在 Qwen3.6、Qwen3.8 `UD-IQ4_XS`、Qwen3.8 `UD-Q4_K_S` 上是同一個數字，
所以那是架構的性質，而且對得上理論。`q8_0` 對不上：
它每個 token 超出 4,198 bytes，
而一層份的 per-token KV 存成 f16 是 4 × 256 × 2 × 2 = 4,096 bytes —— 吻合到 2.5%。

它的形狀就是一個**「一次容納一層」的 dequant 暫存區，隨 context 線性長大**。
f16 不需要這種東西，因為沒有任何東西要被解開。

所以真正的比例是 38.09 / 63.48 = **每 token 成本的 60%，不是 50%**。
一個把 KV bytes 除以二的計算機，會答應你一個這張卡給不出來的 context。
三組實測的天花板：

| | f16 | q8_0 | 增益 |
|---|---|---|---|
| Qwen3.6-27B `IQ4_XS` | 20,224 | 34,816 | +72.1% |
| Qwen3.8-27B `UD-IQ4_XS` | 36,352 | 61,952 | +70.4% |
| Qwen3.8-27B `UD-Q4_K_S` | 19,712 | 34,304 | +74.0% |

它仍然是你手上槓桿最大的一個參數，只是沒有到兩倍。

完整實測：[rtx5060ti-16gb-qwen3.8-27b.zh-TW.md](../results/rtx5060ti-16gb-qwen3.8-27b.zh-TW.md)。

## 代價是什麼

`q8_0` KV 造成的品質損失小到日常使用中很難察覺，
而且這是目前多數本地長 context 設定的標準做法。
對於「會被加總起來」的數值來說，每個值 8 bits 仍然是相當充裕的精度。

`q4_0` KV 就是另一回事了。劣化開始變得明顯，而且是以一種特定的方式呈現：
模型對 context 深處的東西變得模糊 —— 而那正是你當初開長 context 想要的內容。
真要用之前值得先測過。

兩者都幾乎沒有速度成本。在我們的卡上，不論用哪種 KV 型別，
生成速度都平穩維持在約 26 tok/s；這個 cache 是記憶體問題，不是吞吐量問題。

## 實務建議

**先用 `q8_0`。** 它換到大量的 context，而代價是你多半察覺不到的品質差異。

這一切要在「權重本身裝得下」之後才有意義 ——
那部分見 [model-quant.zh-TW.md](model-quant.zh-TW.md)，
裝不下會怎樣見 [spill-cost.zh-TW.md](spill-cost.zh-TW.md)。
沒有任何 KV 設定救得了一個會溢出的模型。

當你在做對精度敏感的事、而且 context 短到負擔得起時，才考慮 `f16`。
只有在 `q8_0` 仍然裝不下、而且你測過輸出撐得住的情況下，才動用 `q4_0`。

```bash
llama-server -m model.gguf -ngl 999 -c 32768 \
  --cache-type-k q8_0 --cache-type-v q8_0 --parallel 1
```

## 一個不太直覺的地方

KV cache 的成本取決於模型的架構，不只是參數量。
Qwen3.6-27B 有 64 層，但其中只有 16 層使用 full attention ——
另外 48 層是 linear attention，state 大小固定、不隨 context 成長。
所以它的 KV cache 比一般同尺寸的 27B 便宜得多。

這就是為什麼某個模型的數字不能直接套到另一個同尺寸的模型上，
也是為什麼「實測」勝過「估算」。相關的陷阱收在 [gotchas.zh-TW.md](gotchas.zh-TW.md) ——
特別是 `--parallel`，它會悄悄把你的 KV 配置乘以 4，
維持預設值的話這整頁講的東西都會被抵銷掉。
